# CLAUDE.md — sleeper-dynasty

Project-specific guidance. See `README.md` for full setup/architecture. Global rules in `~/.claude/CLAUDE.md` still apply.

## What this is

Three-tier monorepo for analyzing Sleeper dynasty leagues:

- `src/sleeper_dynasty/` — **the engine.** Sleeper/KTC/FantasyCalc API clients, season simulator, trade-history builder, three-lens grader, `FileCache`, Google Docs/Sheets output. Also the `sleeper-dynasty` CLI (`cli.py`, entry point in root `pyproject.toml`).
- `api/` — **FastAPI backend.** Thin HTTP layer over the engine. Installs the engine editable. Routes in `app/routes/`, business logic in `app/services/`, Pydantic response shapes in `app/models/`.
- `web/` — **Next.js 14 app** (App Router, RSC, Tailwind). Proxies `/api/*` to the backend.

The engine is shared by the CLI and the backend — changes there affect both.

## Key conventions

- **Five metrics** everywhere, derived per-trade and rolled up per-owner. **Trade Value is a zero-sum swing; the four production metrics are received-only tallies** — points scored by the assets a side *received*, while on that side's roster (no "phantom given" subtraction). Each trade reads as a head-to-head ("104 vs 56"), not a swing.
  - **Trade Value** (`net_ktc` / `snapshot_value_swing`) — today's KTC market-value swing (the one swing metric)
  - **Total Points** (`production_total`) — received-only points, bench included, all weeks
  - **Regular Season Points** (`production_regular`) — received-only started points, weeks before `playoff_week_start`
  - **Playoff Points** (`production_playoff`) — received-only started points in **live title-path winners-bracket games** only; byes, eliminated weeks, and placement games (3rd/5th) count 0. Bracket classification: `engine/playoff_phase.py::classify_playoff_phases` (interprets Sleeper `winners_bracket`/`losers_bracket`).
  - **Toilet Bowl Points** (`production_toilet`) — received-only started points in any losers-bracket game

  The user-facing **labels** (Trade Value / Total Points / Regular Season Points / Playoff Points / Toilet Bowl Points) are the vocabulary — keep them consistent across engine, API, and UI. **Never show "KTC" in the UI — it is "Trade Value" / "Value".** The `lens` query param (`ktc` | `production`) only drives the hero-card verdicts; it is not the headline-metrics selector. The became-grade uses the same taxonomy (`engine/regrade.py::build_became_grade`).
- **Trade detail page = per-player stat tables + asset journey.** Each side renders as a player-first stat sheet (`web/components/TradeStatTable.tsx`): metrics as columns, the haul's players as rows, winner-highlighted totals, a `for <given>` exchange footer. Each received asset tells its **journey** inline — kept assets get an on-roster/dropped tag; **flipped** assets expand to a *linked* `traded to <owner> · <date> → became [terminal players + their stats]`. The **TOTAL reflects what each side realized** (kept assets' own line + flipped assets' *became*). Per-asset data: `engine/trade_grader.py::build_asset_breakdown` + lineage flip metadata (`engine/lineage.py`), assembled in `api/app/services/trade_view.py`. This replaced the old separate "Where it went" + "What it became" sections (`TradeLineage`/`TradeBecame` are deleted).
- **Standings:** `engine/standings.py` reconstructs as-of-week regular-season standings (pure, from each roster-week's `team_points`/`opponent_points`); `api/app/services/standings_snapshot_store.py` persists per-week snapshots per chain (owner-keyed, season-scoped). Self-validates against Sleeper's authoritative `Roster` record. Each trade response carries the side's `at_trade_standing`.
- **Cold-start contract:** dashboard endpoints return `409 cache cold` until `GET /api/league/{id}/refresh` (SSE) pulls + grades the chain and writes the `ChainCache`. Don't change this without updating the frontend's cold-start flow.
- **Trade stories:** the trade detail page leads with an LLM-written verdict + story, following the recap pattern: grounded facts in `engine/trade_story.py` feed `llm/trade_story_writer.py` (`claude-haiku-4-5-20251001`), generated eagerly + incrementally during refresh and cached on the `ChainCacheEntry`. Needs `ANTHROPIC_API_KEY` (refresh still completes and skips stories if unset). Offseason vs in-season labeling lives in `engine/trade_story.py::IN_SEASON_MONTHS` and `web/lib/season-week.ts`. Key wrinkles:
  - **Value-won vs production-won:** the facts packet carries both the trade-Value winner *and* a production head-to-head (`production_winner_user_id` / `production_outcome`, computed in `trade_story.py` over the chain players), so the verdict can name the tension when they diverge ("close on value, blowout on the field").
  - **Point-in-time owner tilt:** per-trade stories get `build_owner_strategy(resolved, …, as_of=trade.traded_at)` — the owner's pattern as it stood *before* that deal, so a story never describes a trade using trades made later. The owner *career* dossiers keep the full-history aggregate (no `as_of`).
  - **KTC sanitizer:** `trade_story_writer.py::sanitize_prose` deterministically strips/replaces the banned term "KTC" (→ "Trade Value"/"value") before caching — the persona bans it but Haiku occasionally leaks it. Never let "KTC" reach the page.
  - **Prompt-version regen:** `story_gen.py::STORY_PROMPT_VERSION` is folded into the skip-hash. Bump it when a prompt/sanitizer/facts-shaping change should regenerate every cached story (the facts-hash alone never moves on a prompt-only edit). It is self-correcting: only the new code can stamp the new version.
- **Auto-refresh (Liveness):** an in-process scheduler (`api/app/services/refresh_service.py`, started in `main.py`'s lifespan) periodically refreshes every already-cached league, keeping the `ChainCache` warm and current. Manual `/refresh` and the scheduler share `refresh_service.refresh_league` (one refresh path). Toggle/interval via `TRADE_GRADER_AUTO_REFRESH` / `TRADE_GRADER_REFRESH_INTERVAL_SECONDS`.
- **Incremental refresh:** a league builds once, then refreshes reuse the prior `ChainCacheEntry` instead of re-grading frozen history. When it's offseason/between-weeks (`api/app/services/nfl_state.py::scoring_in_progress`) **and** there are no new trades since the last build (`api/app/services/refresh_delta.py::new_transaction_ids`, keyed on stable Sleeper `transaction_id`), `grader.py::GraderService.run` copies the prior entry's **frozen rollups** (production series, injury, and the historical rating signals `outcome_signals`/`lineup_signals`/`season_records`/`head_to_head`/`draft_skill_by_season`) instead of recomputing them. It **always** recomputes the cheap "as-of-today" value layer (`grades`/Trade Value, `dynasty_outlooks`, `roster_ranks`, `drafted_picks`). Any new trade, a live NFL scoring week, `force=True`, a missing prior entry, or a `SCHEMA_VERSION` bump → full rebuild (the safe fallback). Relies on the prod cache volume to persist the prior entry across deploys. In-season per-week incremental is documented future work (`docs/superpowers/specs/2026-06-28-incremental-refresh-design.md`).
- **LLM cost control:** prose (stories/blurbs/outlooks) regenerates only past the coarsened skip-hash (`models/_signature.py`), the offseason gate (`grader.py::llm_pass_throttled` — offseason + no new trades → reuse all cached prose), and the time throttle (`TRADE_GRADER_LLM_MIN_INTERVAL_SECONDS`, default 20h). Every call is priced into `llm_costs.jsonl` (see the `llm-cost-analysis` skill). Coarsening or prompt-version changes trigger a one-time full regen on the next ungated pass.
- **Tests never touch the real cache.** `tests/conftest.py` and `api/tests/conftest.py` wrap `FileCache.__init__` with a **tripwire that raises** on any directory under `~/.sleeper-dynasty`, so an escape fails at the offending test rather than silently destroying a developer's warm cache — which it did, repeatedly, before the guard existed. Two subtleties: `FileCache.__init__`'s default was **bound at def time**, so patching `sleeper_dynasty.cache.DEFAULT_CACHE_DIR` was a no-op until the default became call-time resolved (a test asserts `__defaults__` stays unbound); and `grader_io.py` held a **second binding** via `from … import DEFAULT_CACHE_DIR`, which neither the engine patch nor the API env var could reach — it now sources from `get_settings().cache_dir`.
- **Caching:** `FileCache` (engine) and `ChainCache` (backend) persist to `TRADE_GRADER_CACHE_DIR` (`~/.sleeper-dynasty/cache` locally, mounted volume in prod). Historical seasons use effectively-infinite TTL. **Adding/changing a persisted `ChainCacheEntry` field → use the `chain-cache-field` skill** (SCHEMA_VERSION bump-vs-fallback rubric, frozen-rollup vs value-layer placement, test quartet).
- **League phase (dashboard lead selector):** `DashboardResp.phase`/`phase_season`/`phase_week` (`regular`|`post`|`draft`|`offseason`), stamped at refresh by `api/app/services/league_phase.py` and persisted as `ChainCacheEntry.league_phase` — derived from nfl_state + the same per-season min-playoff-start rule as `production_week_phases`, so the two can never disagree. Draft window = Sleeper draft `drafting`, `pre_draft` with start_time ≤ 7 days out (`DRAFT_WINDOW_DAYS`), **or `complete` when that draft's season is the current NFL season and the regular season has not started** — the window stays open until week 1 kicks off, so a just-finished draft is still the story rather than flipping straight to "offseason" the instant the last pick lands. `regular_season_started` is tri-state: an unavailable nfl_state (`None`) keeps the window shut rather than guessing. Format-neutral — redraft and keeper drafts open it exactly as rookie drafts do. Pre-feature caches read "offseason" until the next refresh.
- **Per-lens trade verdicts:** trade detail carries `winners_by_lens`/`margins_by_lens`/`call`/`lens_tally` (`trade_view.py::_realized_lens_totals` + `_lens_verdict`), computed from each side's **realized** breakdown rows (kept assets' own line + flipped assets' became — the stat table's TOTAL reading), so summing visible rows reproduces each margin. A lens both sides left at 0 is unscored (excluded from call/tally); scored ties count for nobody. `winner_user_id`/`lopsidedness` stay received-KTC (hero card) — with flips the value lens can legitimately name a different winner.

- **League chain:** the grader walks `previous_league_id` back to league origin from the entry-point season.
- **Dashboard lead (one skeleton, four sources):** `HeadlineMoves.tsx::selectLead` picks by `DashboardResp.phase` — `regular` → week recap, `post` → **bracket watch**, `draft` → **draft review**, `offseason` → trade of the week. Always three figure cells at every width, so the page never reflows across the season. Two of the four are backed by persisted blobs stamped at refresh, both **value layer, always recomputed, never frozen**, both **no SCHEMA_VERSION bump** (display data, `league_phase` precedent): `bracket_watch` (`engine/playoff_phase.py::build_bracket_watch` — entrants collected across *every* round because the top seeds have round-1 byes; only a **played title-path** loss eliminates; placement games are not the title path) and `draft_review` (`engine/draft_results.py::build_draft_review` — each pick graded against its own class via `slot_delta` = draft position minus production rank, so no ADP table can go stale). `bracket_watch` returns None when the league has no bracket at all (nothing to watch), rather than emitting a hollow entrant list. `draft_review` returns results with `graded: False` the moment the draft completes (no productions played yet), reserving `None` for an unreviewable class (no picks, or fewer than two); an unplayed draft class is all zeros, and naming a "best pick" out of ties would invent one. The bracket watch's playoff-points figure is read from the standings rows the same response already built, so the lead can never disagree with the table beneath it. **Neither is verified against live data yet** — `post` only happens in Dec/Jan and `draft` only in the draft window.
- **Platform ingestion protocol:** `api/platform.py::LeaguePlatform` is the contract every platform implements — anything not on it is unavailable to the engine, which is what stops a platform's encoding leaking inward. `SleeperClient` implements it; `YahooAdapter` is the second implementation (in progress). Routing comes from the league id's **shape** (`platform_for_league_id`: all-digits → Sleeper, contains `.l.` → Yahoo), so no cache filename, membership row, or URL carries a discriminator and nothing needed migrating. Unrecognized shapes raise rather than defaulting. Three normalizations matter: the protocol asks for a **phase map**, not brackets (Sleeper derives one from winners/losers brackets via `get_phase_map`; Yahoo's scoreboard marks matchups directly) — a consolation game is `toilet`, never `playoff`; trades and drops are **separate** calls (Sleeper filters one mixed feed, Yahoo has typed collections); and **every `player_id` crossing the boundary is a Sleeper id** (`api/yahoo_ids.py` maps `yahoo_id`→`sleeper_id` from DynastyProcess's `db_playerids.csv` — an unmapped player is **dropped, never zero-priced**, and R's literal `"NA"` null must be filtered or it becomes a catch-all key). Two gotchas live in `SleeperClient`: `_all_week_transactions` fetches the 18 weeks **concurrently** and **memoizes one league id** — Sleeper serves trades and drops from the same feed, so without the memo each protocol call re-walks all 18 weeks and doubles the request count. Test doubles borrow the real derivation via `tests/helpers.py::wire_transaction_protocol` rather than reimplementing the filtering. **`League.format` replaced the Sleeper-specific `league_type` int** on the domain model.

- **Franchise Rating (`/gm`, platform-wide):** a transparent **two-pillar** composite (v2) — `V2_PILLAR_WEIGHTS["v2_dynasty"]` = `0.60·Results + 0.40·Assets`, scaled to a **1500-centered** number (clamped 800–2200) and mapped to a **letter grade** via `engine/gm_rating.py::rating_to_letter` and to a **competitive-window stage** via `rating_to_stage` in the same file (Dynasty / Contending / Competing / Retooling / Rebuilding, `_STAGE_SD` at ±0.90/±0.30) — one model, so the stage on a standings row and the stage on the franchise page can never disagree. `rating_to_stage` takes an optional `sd`: **each league's own realized rating spread**, derived once by `franchise_redesign.py::league_stage_sd` and floored at `STAGE_SD_FLOOR` (0.5·`POINTS_PER_SD`) because at sd→0 every edge collapses to 0 and a flat league would grade **everyone** Dynasty. `sd=None` keeps the fixed reference bands. The centre stays `BASE`, never the league mean, which drifts only where the 800–2200 clamp bites. (fixed, sd-derived bands in `LETTER_BANDS`, rewritten for v2: **A+ to D− with no F** — a twelve-owner league spans roughly ±1.75 sd of composite, so an F band could only ever fire by construction or never — with `C+` restored and `C` widened relative to its neighboring bands, C still = league-average). This is v2 of the model; v1's three-pillar tree (`results_led`/`keeper_led`/`redraft_led`, with a **Skill** pillar of trade/draft/lineup signals) is **retired** — Skill measured noise, not signal: nothing in it persisted year to year (draft skill correlated ~+0.10 season over season, lineup skill ~+0.04, and both trade signals were *negatively* self-correlated). v2 drops Skill and measures it through its consequences instead. **Results** = `expected_wins` (all-play win rate, so schedule luck is removed), `playoff_success` (a berth counts half a round win, plus rounds won, plus a championship bonus), `luck` (actual minus expected, orthogonal by construction) — the old `made_playoffs`/`final_seed`/`points_for_rank` signals are gone from scoring. **Assets** = `roster_value_share`, `young_core_share` (share of roster value held by players 25-and-under; replaced a straight mean-age signal that mostly measured bench filler), `draft_capital`. Format trees: `v2_dynasty`/`v2_keeper` share the 0.60/0.40 split (keeper drops `young_core_share` — two or three keepers isn't a young roster — and renormalizes the Assets survivors over their combined weight, preserving their ratio); `v2_redraft` is **Results only** (Assets dropped, not zeroed, since nothing carries over between seasons for redraft and a zeroed pillar would still consume its weight and compress every grade toward 1500). Recency decay uses a **two-season half-life** (a chosen prior, not a measured one), clamped so a season ahead of the anchor can't outweigh it. `SCALE` is `POINTS_PER_SD / REFERENCE_COMPOSITE_SD` rather than assuming a composite sd of 1.0. `REFERENCE_COMPOSITE_SD` = **0.6854, measured 2026-08-17** on the reference league (12 owners, 2023–25, rebuilt at SCHEMA_VERSION 17, scored under `v2_dynasty`) — it replaced a 0.906 stand-in that was the *Results-pillar* sd of the old tree, an over-estimate **by construction** since a 0.60/0.40 blend of imperfectly-correlated pillars has a strictly smaller sd than either pillar alone (that error cost about a quarter of the ladder: 5 distinct letters instead of 7, four owners sharing the bottom band). The bands are therefore **honestly measured but n=12, one league — not proven to generalise**; re-measure with the `franchise-rating-calibration` skill whenever the tree, the signals, or the bands move. Note the pillar z's this scales are **weighted averages of correlated signal z's**, so a pillar's own sd is well below 1.0 — never read "z ≥ 0.8" on a pillar as a ~21st-percentile cut. The letter is a **percentile within your league**, not an absolute or cross-league scale — the methodology page states this explicitly. `compute_gm_ratings` returns a full breakdown (pillar → signal → raw/z/weight/contribution) so every point is traceable. Live rating assembled by `api/app/services/franchise_redesign.py::live_ratings` (single source of truth). Signals persisted on `ChainCacheEntry`: `outcome_signals` is a **frozen rollup** on incremental reuse; `outlook_signals` is **not frozen** and always recomputes (current roster value/youth don't wait for a rebuild); `lineup_signals` is also frozen but no longer scores anything. Retired v1 signals (`championships`, `made_playoffs`, `final_seed`, `points_for_rank`, `youth`, `roster_value`, `draft_skill`, `lineup_skill`, the trade signals) are **still persisted** — they have non-scoring consumers: the GM-blurb LLM facts packet reads `championships`/`made_playoffs` off `outcome_signals`, and the owner Outlook tab's draft-capital ranking reads off `outlook_signals`. **`draft_skill` is now computed, persisted and passed into the component but rendered NOWHERE** — the standalone display was its only surface and went with the section-header meta lines. Deliberate: v2 dropped draft skill from the rating as measured noise, so publishing an ordinal for it implied more than it means. `draft_skill_by_season` still feeds the Draft tab's per-pick grading. Cache `SCHEMA_VERSION` **17**. `season_ratings` (`leaderboard.py::compute_season_ratings`) is **empty under v2** — an all-time decayed tree can't produce a per-season rating, and fabricating one would feed a false zero to the year-over-year delta and the Biggest Riser card, so its remaining caller (`_rise_hero_stat`) falls back to its existing "no signal" path (`_backfill_yoy` was **deleted** with the window model — its feed had returned `{}` since v2). Per-NFL-week rating snapshots (`rating_snapshot_store.py`) are **stamped with the model** that produced them (`v1` vs `v2_dynasty`/etc.), so a v1 rating can never be diffed against a v2 one; they drive the trend arrow. The owner hero shows the letter, the rings strip, and the **LLM franchise blurb** — `ReadPanel` in `HeroBand.tsx`, fed `franchise_lead`/`franchise_blurb`/`franchise_segments`. Two claims here used to be **backwards**, and the code is the authority: the mono **receipt is gone** (it carried roster rank, rating, trend and biggest-drag under the letter for one release; `HeroBand.tsx`'s own docstrings argue the removal, and with it gone there is no other route to those figures in the band), and the **franchise-blurb pipeline is LIVE, not deleted** — `grader.py` runs the `franchise_blurbs` stage (`generate_franchise_blurbs` + `FranchiseOutlookWriter`), it persists on `ChainCacheEntry.franchise_blurbs`, and `owner_view.py` surfaces it. It is the blurb, not a receipt, that now says *why* the grade reads the way it does, which is why it sits in the hero rather than a tab. The per-pillar highlights are a separate, smaller pipeline (`GmRatingBlurbWriter`). Pure + unit-tested. **Term: it is "Franchise Rating" in all UI; "GM Rating" is retired.**

And the label anchor was binary at exactly 0/100 while clipping is continuous — `labelAnchorPx` now clamps the label centre into the track at any position. `MIN_SEP_PCT` is likewise derived from a measured pixel width, not a fixed percentage, because a label is fixed px while a percentage of the track shrinks with the viewport; and **draft** (`DraftSection`, no section-header meta — every top-right meta line on this tab was removed, which is what left `draft_skill` unrendered). The independent Strength × Trajectory window model is **retired**: over half its Trajectory axis could not discriminate (40% `draft_skill`, which v2 deleted as measured noise; 15% `yoy_momentum`, a dead constant giving every owner exactly 7.5). `WindowSection.tsx` is deleted. **jsdom lays out no CSS Grid and `furniture-rules.test.ts` has no rule for track counts, label collision or width budget** — four browser-only defects here (mobile horizontal scroll, label overlap, an edge-clamped label clipped by `Panel`'s `overflow-hidden`, and a run-on header) were found only by a live headless pass, so a green suite is not evidence this tab lays out correctly.
  - **Draft** (gated on `draft_picks_by_season`): The **"How past picks panned out"** table (`PastPicksTable.tsx`) — one row per drafted pick with value-arc + five-metric production, plus: a **Status** chip (`roster_status`: rostered/traded/dropped, the pick's *current* standing for the drafting owner), a **GS** column (`games_started` = weeks started for that owner, all phases, owner-gated), a **totals row** summing every numeric column, and an **All-Time** entry in the year selector (`flattenAllTime`/`columnTotals`/`ALL_TIME` in `pastPicks.ts`). Per-pick data: `engine/draft_results.py` (`build_drafted_pick_results` + `started_games_while_on_roster` + `derive_roster_status`); grader builds `current_holders` + a `traded_away_set` from trade `given` sides; surfaced via `DraftPickResult` (`api/app/models/owner.py`) + `owner_view`.
  Cross-links: `/gm` rows and trade-detail owner names link to the owner page.
  A "vs You" band (auto viewer resolution via the soft Sleeper link, rival picker fallback) sits between the hero and the tabs, and a copy-receipt action (`web/lib/receipts.ts` + `ReceiptButton`) on the owner tab bar and trade verdict composes claim + deep link for the group chat.
- **Draft grading (all formats):** `engine/draft_class.py::build_draft_classes` decides once what each Sleeper draft *is* — every format question about a draft is answered there and nowhere else. **`settings.player_type` restricts the selectable POOL — it does not name the kind of draft** (`1` = rookies only, `0` = open pool). So dynasty selection uses it as one signal, not the whole rule: `1` is a rookie class outright whatever the season (which is what keeps a rookie class held in the origin season alongside a startup), while `0`/absent falls back to the origin-season test, because plenty of dynasty leagues run their annual rookie draft with the pool left open so a manager may take a veteran instead — verified live on a real 4-round rookie draft with 28 of 48 picks rookies sitting at `player_type` 0. Reading `0` as "startup" discarded that league's only draft every year. Redraft and keeper are unaffected: they **grade every season's full draft including year one**. An auction is ingested with `gradeable=False` — its `pick_no` is chronological, so a slot delta would be noise. Grading runs on **three independent baselines, never blended**: the league-native peer delta (`draft_signals.py::draft_skill`, available in every format — under v2 this feeds only the owner page's standalone draft-skill display, since Franchise Rating dropped its Skill pillar and draft_skill along with it), the ADP delta, and the projection delta. ADP and projected points both come from `SleeperClient.get_projections` — one call, native Sleeper `player_id`, no crosswalk, covering K and DEF which FantasyCalc's redraft set does not. **`999.0` is the undrafted sentinel and must be filtered** (`engine/draft_baselines.py::ADP_UNDRAFTED`) — same trap as DynastyProcess's `"NA"`. **ADP is pinned to each draft's own date, not to refresh time** — `api/app/services/adp_snapshot_store.py` writes a dated daily snapshot (`adp/daily/YYYY-MM-DD.json`, the `KtcSnapshotStore` pattern) on every refresh, and `resolve_for_draft(draft_id, drafted_on)` picks the snapshot on-or-before that draft's `last_picked` date, **never after**, then freezes it write-once per `draft_id`. A league drafting Aug 1 and one drafting Aug 26 face different markets and must grade against their own; capturing at refresh time would have stamped August ADP on a May draft. Grading against live ADP is grading against hindsight, so ADP columns work **going forward only** — a draft predating the first daily snapshot has no baseline, permanently, and grades on the peer baseline alone. **Keeper and auction picks are shown but never scored** — a keep is not a draft decision, and an auction's `pick_no` is the order money changed hands. That exclusion is applied at *every* consumer, not just `draft_skill`: `build_draft_review` and `draft_board_view` both filter on one shared `scored` list, so the ADP grade and the production ranking can never carry two different definitions of "this owner's draft". Two consequences that are deliberate: **`graded` is computed over scored picks only** (keeper points are real but are not this draft's doing, so an all-keeper class cannot claim to be graded while the owners section has nothing to rank), and **every owner who made a pick is listed** even with no scorable ones — an absent row reads as "this owner had no draft", which is false, where a null figure reads as "no grade", which is true. Results and grades have **different availability dates**: `build_draft_review` and the board return `graded: False` with the picks intact for a class that has not played — and likewise for one with nothing scorable at all, because "the class is in the books, N picks" is worth saying even when nothing can be graded; returning None there sends the lead to trade-of-the-week and takes the only link to the board with it. Ungraded `total` counts every pick **made** (that N means the draft); only the graded denominator narrows to scored picks. None is reserved for a season with fewer than two picks. Surfaces: the league-wide board (`web/app/league/[id]/draft/[season]/page.tsx`), the owner **Draft** tab (gated on `draft_picks_by_season`, **not** on `outlook` — that gate is what used to hide draft grading from redraft leagues entirely), and the draft-window dashboard lead.
- **Draft board (`/league/{id}/draft/{season}`):** the whole class on one screen — a season selector, an **Owners** rollup, the **Picks** ledger, and the **Going in** panel. Every pick carries a **rookie-ECR baseline** pinned to the draft's own date (`EcrBoardStore`, same write-once-per-`draft_id` freeze as the ADP store) and a **slot +/-** (draft position minus board rank), so a class is assessable on draft night, months before it plays. Owner rows rank by **Points Above Round** (`engine/draft_par.py`), not raw Total Points — raw points rank draft POSITION, since whoever picks first tends to win, and PAR is zero-sum within the class so it rewards drafting well from a bad slot. Column templates live in `web/lib/draft-columns.ts` and are **width-gated arithmetic, not taste**: the desktop tables render behind `min-[910px]`, but the grid only ever sees **860px** (`gate − 48px Shell padding − 2px Panel border`), and `web/tests/draft-columns.test.ts` fails the build on any template over it. Getting that subtraction wrong once shipped a regression — a breakpoint is the viewport, not the space the grid gets.
- **Hit / Average / Bust (cohort verdicts):** `engine/rookie_cohorts.py` grades a pick against **what comparable picks actually scored** — no invented thresholds. A pick is a Hit above the 75th percentile of its cohort and a Bust below the 25th; cohorts are keyed by **(ECR band, seasons held)** with cumulative totals, so a pick held one season is judged against what its peers had accumulated after one, never against their careers. The committed history (`data/rookie_stats.json.gz`, regenerated by `scripts/extract_rookie_stats.py`) carries **raw components, not points**, because 6-point passing TDs move a QB-heavy bar ~30 points against 4-point ones — it is priced per league at refresh. Three refusals, all "wrong is worse than absent": a cell under `min_n`, a cell whose `p25 == p75` (a bar that cannot discriminate would call any positive total a hit), and a league pricing something unexpressible. **That last rule is population-aware, and must stay that way.** It once asked "does this league price anything I can't express?" — every Sleeper league prices a kicker and a defense, so it refused **every league that existed** and the Verdict column shipped rendering nothing on every account. The question that decides the answer is "can what I can't express change the total of a player I am comparing?", so `_IGNORABLE` exempts kicker/team-defense keys (impossible for an offensive rookie board) plus a small **measured** residual (`fum`, individual ST credits: ±5 points moved 3 of 69 verdicts, each already on a percentile edge, against bars spreading 26–472). Unclassified keys still refuse — the allowlist is the whole safety property. **Keepers are never judged** (`verdict_for_row` refuses them outright): only auction picks fell out for free via `gradeable`, a keep inside a gradeable rookie draft gets a baseline like any other row. The board's Owners table rolls the same per-pick strings up as **Hit/Bust**, never recomputed, so the owner figure equals the rows beneath it; an owner with no judged picks reads an em-dash and sorts as ungraded, not as zero. `OWNER_GRID_GRADED_ADP` deliberately does **not** carry the column — it is already 858px against the 860px budget — and `ownerGrid` checks ADP first.
- **"Going in" panel (draft-day roster reconstruction):** what each owner's starting lineup looked like **when the draft opened**, and what the draft did about it. `engine/roster_asof.py` seeds from the prior season's final played week (matchups' `players`, **not** `get_rosters`, which is live state and would re-apply offseason moves) and replays transactions; `engine/draft_needs.py` solves each lineup and checks it against a **league-native replacement line** — the demand-th best player at that position across the league pool. **`as_of` is the draft's `start_time`, not `last_picked`.** A slow-clock rookie draft is not an instant (83 hours on the reference league in both 2026 and 2025, 47 in 2024), and what managers do during those days is clear bench room for the picks they are about to make: 17 drops and 5 trades across 7 of 12 rosters inside one window. Rewinding to the close applied that cleanup *before* reading the holes and manufactured holes in the panel's headline column. `last_picked` is still correct for the ECR board pin, which freezes write-once and matches the ADP store. Two rules the UI obeys: an **empty** starting slot is not a hole (`margin=None`, `is_hole=False`) — whether it should be is deliberately left undecided by arithmetic, and the earlier `-inf` sentinel 500'd the whole board; and an owner with no holes still renders a real reading (the softest slot's own margin), never an em-dash. Panel rows take their order from the **sorted Owners table above** rather than the engine's Sleeper-roster order — the two list the same owners and shared no position at all before that, though the panel still has no sort control of its own. **Keeper leagues are excluded, and the obvious fix does not work** — see the measured dead end in `grader.py` above the gate: seeding from `is_keeper` picks shrinks each position's pool to roughly its own demand, so the line collapses onto the worst player in it and **0 of 12 owners get a hole** (against 6 of 12 for dynasty-shaped rosters). A working version must decouple seed from pool, which is a signature change to `build_draft_needs`, and wants a real keeper league to validate against — none of the cached leagues is one.
- **Became grade (Lineage):** alongside the *direct* grade, each trade carries a parallel "what your haul became" grade — the same five metrics (Trade Value / Total Points / Regular Season / Playoff / Toilet Bowl) recomputed on the **terminal players** the side's assets turned into. Bounded "anti-spiderweb" walk (shared with the Phase-1 lineage tree in `engine/lineage.py`): a received **player** gets exactly **one flip** (results are terminal); a **pick** is followed through flips/drafts until it resolves to players (terminal); a terminal player traded onward is a *new* trade's story. Per-side totals, not a zero-sum swing. `engine/regrade.py::build_became_grade` computes it using `engine/lineage.py::terminal_assets`; refresh caches it incrementally; exposed on the trade detail response and surfaced inline in the trade journey (the flipped-asset expansion in `web/components/TradeStatTable.tsx`).
- **Production timeline ("Did it pan out?"):** the trade detail page charts each side's **cumulative production over the trade's tenure** (`web/components/ProductionTimeline.tsx` inside `TradeProductionCard.tsx`). It is **chain-aware**: a received player's line runs while held; a **dropped** asset's line *stops* at the drop; a **flipped** asset's line *continues* onto what the asset became (lineage). Calendar x-axis with season boundaries; overlay bands for **playoff weeks** and **injury-OUT** stretches; **drop/trade departure markers** labeled with the player's name. Built in `grader.py::compute_production_series_payload`; the trade response carries `production_week_phases` (per-week "pre"/"post" playoff phase) and `departures` (per-player drop/trade events). Metric switch reuses the five-metric taxonomy.
- **Injury context:** games-missed-by-phase plus live status for each received player. Source map from **nflverse** weekly rosters (`engine/injury_data.py`, fetched via `api/nflverse.py`); the games-missed-by-phase classifier is `engine/injury.py`; live in-season status is `engine/injury_live.py`. Computed during refresh (`grader.py::compute_injury_payload`) and persisted on `ChainCacheEntry`; surfaced as the **Injury Impact** block and the chart's OUT bands. Gotcha: a week counts as **played only when the player scored > 0** — mere presence in `players_points` includes IR players listed at 0.0, so presence-based detection silently misses real injuries.
- **Side Bets (dashboard Bets tab + owner Track Record card):** a manual 1-vs-1 money ledger between owners — freeform description, integer-cents amount, `open`/`settled`/`push`/`void` lifecycle, per-owner won/lost/net rollups. Lives in **Postgres** (`side_bets`, migration `0007`), never the rebuildable chain cache; league-gated endpoints under `/api/league/{id}/bets` (routes `api/app/routes/bets.py`, pure domain rules + ledger math in `api/app/services/side_bets.py`). Rules: **money is integer cents only** (`web/lib/money.ts` renders dollars); **void replaces delete** (history is never destroyed; field edits only while `open`); winner must be one of the two sides; **standalone** — never feeds Franchise Rating, standings, or stories; these endpoints never `409` on a cold cache — owner names degrade to raw user_ids.
- **League capabilities (format gating):** `engine/capabilities.py::derive_capabilities` describes what a league supports — `format` (`dynasty`|`keeper`|`redraft`) plus three **evidence-based** booleans (`future_picks` from whether any trade actually carried a pick, `multiyear_history` from chain length, `roster_continuity` from format). It reads `League.format` off the league and holds **no platform knowledge** — the Sleeper `settings.type` int is mapped in `api/sleeper.py::format_for_type` where it belongs, so any object with a `.format` string can be described (see the platform-protocol bullet). Stamped at refresh and persisted as `ChainCacheEntry.capabilities` — value layer like `league_phase`, always recomputed, **no SCHEMA_VERSION bump**; empty on pre-feature caches and reads back as full dynasty. Three consumers: Franchise Rating picks a weight tree (`franchise_redesign.py::model_for` → `v2_dynasty`, `v2_keeper`, or `v2_redraft` — v1's `results_led`/`keeper_led`/`redraft_led` are retired); redraft drops the Assets pillar outright (`Results: 1.00`, not a renormalization of two pillars down to one — nothing carries over between redraft seasons, so there's no Assets subject at all, and a tree summing to <1.0 would silently compress every grade toward 1500), while keeper keeps the 0.60/0.40 pillar split and instead renormalizes *inside* Assets, dropping `young_core_share` and rescaling `roster_value_share`/`draft_capital` over their combined weight to preserve the ratio; the value layer picks a FantasyCalc set (`fetch_fantasycalc_values(dynasty=…)`; the redraft set is thinner, ~200 vs ~474 players, and unmatched players resolve to zero — **never fall back to dynasty values**); and the **Outlook surfaces are dropped for redraft** — `owner_view` omits `outlook` (so `OwnerDeepDive.tsx` drops the tab), and `aggregations.py` leaves `StandingRow.window`/`draft_capital_value` as `None`, on which `StandingsTable.tsx` omits the Window / Draft cap columns outright (`hasOutlookColumns`). Absence, not a blank column. `strength_score`/`trajectory_score` and the `s/t` column are **gone** — they were the retired window model's two axis scores. `window` survives as a **derived** read of the rating and stays gated on `_outlooks_apply`: `ratings` is NOT redraft-gated though `dynasty_outlooks` is, so an ungated derivation would label every redraft franchise "Dynasty". **The franchise blurb is a third dropped surface, not a retired one** — it is the Outlook prose for the same pillar the tab was just dropped for, so `owner_view.py` suppresses it under redraft (`{} if is_redraft`) and the field reads `None`, rendering nothing. Absence, not an empty state. An unknown format falls back to `v2_dynasty`. Leagues stay self-contained — nothing is pooled across them. **Snapshots are namespaced by valuation source** (`snapshots/` dynasty, `snapshots-redraft/`): redraft chains accrue their own dated price history rather than borrowing dynasty's, which restores at-trade/aged/realized repricing **going forward only** — FantasyCalc publishes no historical endpoint and `capture()` writes today, so trades older than a league's first snapshot keep live pricing permanently. For redraft this is a **precedence inversion, not a parameter flip**: KTC (`fetch_ktc_values`) is skipped entirely rather than fetched-and-gap-filled, so FantasyCalc's redraft set becomes the sole player-value source instead of dynasty's gap-filler role. Two consequences follow, both surfaced in the coverage warning rather than hidden: **redraft leagues do trade draft picks on Sleeper** (that claim from an earlier plan draft was wrong), but with KTC skipped the pick-value tables (`build_pick_value_table*`, sourced from the raw KTC blob) come out empty, so **any traded pick in a redraft league prices at 0** — real redraft pick valuation is a deferred follow-on; and `KtcSnapshotStore` is one store **per install, not per league** (`grader.py`), so every dynasty league's refresh would otherwise write dynasty prices into it and `compute_realized` would silently apply them to a redraft trade's `received_ktc` — it is gated to `None` for redraft chains (`is_redraft_chain(chain)`). The accepted cost is **three** things, not one: redraft leagues have no at-trade valuation, no aged valuation, **and no realized repricing** — `compute_realized`/`make_price_providers` sit inside the same `snapshot_store is not None` block, so `received_ktc` and every `breakdown[].ktc` keep their *today, full-value* reading instead of being repriced to what the owner realized (held → today, flipped → flip date, dropped → 0). A redraft owner who trades for a player and cuts him in week 3 still sees that player's full current Trade Value credited, which **contradicts** the "the TOTAL reflects what each side realized" contract above. That is a known gap, not an intended reading: restoring it needs a redraft-native price history (FantasyCalc redraft has no per-date snapshots) and is deferred.
- **Backups (R2):** a daily in-process job (`api/app/services/backup_service.py`, started in `main.py`'s lifespan) dumps Postgres to gzipped JSONL via SQLAlchemy reflection and tars the cache volume to Cloudflare R2 under `backups/<run-id>/`. **`manifest.json` is written last and is the run's commit marker** — a prefix without one is incomplete and `scripts/restore.py` skips it. Nothing in `api/` calls delete or list, and nothing may add one — that is hygiene, **not an access control**: R2 issues no put-only permission group, so the app's credential is **Object Read & Write** and can delete and overwrite. A **bucket lock rule** (required setup step) plus the lifecycle rule are the real protections — **R2 has no object versioning**, so locks are the substitute, and they beat lifecycle rules so a locked object cannot be reaped early; timestamped prefixes only make a *blind* overwrite hard. The dump handles **scalars only** — `test_backup_dump.py::test_every_column_type_is_dumpable` fails the build if a migration adds JSONB/bytea, and `_encode`/`_decode` must be extended before such a migration merges. Restore needs a separate read-scoped token and runs from an operator machine, never the app. **`api/tests/test_backup_roundtrip.py` proves the whole dump→archive→manifest→restore chain offline** (fake R2 as an in-memory dict); it does not prove anything about the real R2 network path, real Postgres, or `scripts/restore.py`'s own CLI/production-guard behavior. **Those were closed by a live dry run on 2026-08-13** — run `2026-08-13T19-08-45Z` restored into a scratch Postgres 18.4, whole-table hashes matching prod for `users`/`league_memberships`/`side_bets`, `timestamptz` exact to the microsecond, all three `ChainCache` entries loading at schema v16 with 86 cached stories, dashboard 200 (not `409 cache cold`). See README's Backups and restore section. Both Cloudflare guard rails are live on prefix `backups/`: a **bucket lock rule** (30-day retention — the control that stops the app's own credential erasing history) and a **lifecycle rule** (delete after 30 days). Backups run daily at 09:00 UTC.

## Auth & multi-tenant

The web app is **login-gated** (NextAuth + Google; `web/middleware.ts` redirects anonymous users to `/login`). **`config.matcher` is an explicit, fully-anchored allowlist, and both properties are load-bearing.** It previously excluded metadata routes by *unanchored* substring (`.*icon`), so any path merely containing one skipped the gate — `/league/123icon` returned 200 unauthenticated on **every dynamic route**, since dynamic segments supply the substring. No data leaked (the proxy and the API still refuse anonymous callers, and every path parameter is a numeric platform id, so a bypassing URL is necessarily a corrupted one), but the page shell rendered. **Never hoist the matcher into a `const`:** Next parses `config` from the AST and cannot resolve an identifier — it emits a *warning*, falls back to the **catch-all**, and then gates `/api/*`, every og route and `/_next/static/*`, which builds and deploys silently. `web/tests/middleware-matcher.test.ts` reads the file from disk, drives it through Next's own `getMiddlewareMatchers`/`getMiddlewareRouteMatcher`, and globs `app/` to derive the expected metadata URLs, so a renamed og route fails the suite. The allowlist admits `opengraph-image-<hash>` (route groups) and `opengraph-image/<id>` (`generateImageMetadata`) because gating a metadata route is worse than the bug: Next gives them no session even for a signed-in visitor, so every unfurl silently degrades to the fallback card. `web/auth.ts` owns the OAuth session; `web/lib/auth-server.ts` mints a short-lived HS256 token (signed with `AUTH_BACKEND_SECRET`) that the FastAPI backend verifies (`api/app/auth/`, secret `TRADE_GRADER_AUTH_BACKEND_SECRET` — **the two must match** or every request 401s). The web→api proxy (`web/app/api/[...path]/route.ts`) attaches that token and 401s anonymous calls, so anonymous `/api/*` (incl. `/api/health`) returns 401 by design. Identity (users, league memberships, sessions) lives in Postgres via async SQLAlchemy + Alembic (`api/migrations/`, run as a deploy step); `TRADE_GRADER_DATABASE_URL` unset falls back to SQLite. `/` is the multi-tenant "My Leagues" home; `ALLOWLISTED_LEAGUE_ID` lets signed-in users view one league without a membership row. **Admin support access** sits beside that bridge in `api/app/auth/deps.py::require_league_member` and has the same shape — an admin may `GET`/`HEAD` any league without a membership row, but writes still 403, because there is no undo on an owner-name override or a bet mutation and a debugging session must not mutate a stranger's league (`/refresh` is a GET, so warming a cold cache still works). It lives at that one chokepoint precisely so no league router can miss it and no future one can forget it. `web/app/league/[id]/layout.tsx` makes the access visible on every league route at once — the condition is **inferred** ("this league is not in your `/api/me/leagues`") rather than a server flag, which is sound because a non-member non-admin is refused at the API; a failed lookup shows the banner, since over-warning is the safe direction. Note `is_admin` is re-derived from `ADMIN_EMAILS` on **every** upsert (`deps.py`), so seeding the DB column does not grant admin — tests must set the env var. Deliberately **no audit trail** (single admin); revisit before granting `is_admin` to anyone else. Design: `docs/superpowers/specs/2026-08-12-admin-league-access-design.md`.

**The `og-card` principal (sessionless reads, deliberate exposure).** The four `opengraph-image.tsx` routes render real cards for link unfurls. A crawler carries no session and Next's metadata routes get none even for a signed-in visitor, so they mint their own token (`web/lib/og-token.ts`, `import "server-only"`, 2-minute TTL) signed with the same `AUTH_BACKEND_SECRET` but carrying **`scope: "og-card"` and no identity claims** — no `sub`, no `email`. Two rules bound it, and they are the whole design: **`get_current_user` 401s the scope outright** before reading any claim, which is what keeps card traffic out of `users.upsert_from_token`/`touch_activity` (a crawler must never mint a user row or inflate active-days) and simultaneously seals every router depending on it; and **`require_league_member` admits it only for GET/HEAD on four anchored path regexes** (dashboard, leaderboard, owner, trade detail) — everything else, `/refresh` included, falls through and 401s. `league_guard` is now `[Depends(require_league_member)]` alone: the guard resolves the user *itself* (a direct call, not `Depends`) so the og branch can short-circuit **before** any DB touch. Authentication is not weakened — `_decode` runs first and there is no path past it without a valid signature. **This exposes league card data to anyone with the URL, and that is accepted**: it is the only way a crawler renders a real card. Widening `_OG_CARD_READABLE` widens that exposure — note `GET /bets` and `GET /bets/summary` do *not* depend on `get_current_user`, so the path allowlist is the only thing keeping them shut. The four card endpoints carry `@limiter.limit(lambda: …rate_limit_og_card, exempt_when=og_card_only)`, keyed **per league** (`og-card:{league_id}`) so abusing one league cannot starve another's unfurls, and scoped by `og_card_only` so signed-in users on those same routes — they are the main app's own routes — are never throttled. Setting the rate-limit key alone meters nothing: there is no `SlowAPIMiddleware`, so only decorated routes are limited, and `test_og_card_reads_are_rate_limited` is the regression test for exactly that gap.

## Product telemetry & engagement (admin-only)

- **Active-days metric:** `users.active_days` / `users.last_active_at` count the distinct UTC calendar days a user was active. Stamped server-side in `get_current_user` via `users.touch_activity` (gated to one write per user per UTC day; steady state stays a pure read). This **replaced the retired login-count** (the old NextAuth `signIn` → `/api/me/login-event` path and `web/lib/login-event.ts` are gone). Surfaced on the `/admin` users table (active-days + last-seen).
- **Pageview telemetry:** a client beacon (`web/components/Telemetry.tsx`, mounted once in `web/app/layout.tsx`) posts each route change to `POST /api/events` via `navigator.sendBeacon` — same-origin, so the proxy attaches the backend token. The endpoint is **user-scoped (`get_current_user`), NOT league-gated**, rate-limited, and authenticating through it also stamps active-days. `api/app/services/route_normalize.py::normalize_route` maps the raw path → low-cardinality route template + league id (pure, unit-tested); a `page_events` row is stored (`api/app/db/models.py::PageEvent`, migration `0006`). **Query strings are never persisted.** Aggregations live in `api/app/repositories/events.py` (dialect-portable — daily bucketing in Python, no SQL date funcs).
- **Admin dashboards** (`api/app/routes/admin.py`, all `require_admin`): active-users (DAU + 1/7/30-day) on the `/admin` Usage section; per-league activity columns on the Leagues table; a per-user drill-down page `web/app/admin/user/[id]/page.tsx` (recent pages + activity). Deferred by design: a global "top pages" view, retention/rollup/pruning (events kept raw), funnels.
